# XZA100 and XZB100 Linux cells

These configurations describe one root Linux and one CPU-only Linux inmate on
XZA100 (Phytium D2000) or XZB100 (NVIDIA Tegra234/Orin). Each root initially owns
CPUs 0–7; creating the inmate transfers logical CPU7. The inmate sees one CPU,
512 MiB of private physical RAM, a virtual console and two ivshmem endpoints.
Physical storage, network, FPGA, GPU, CAN and other peripherals remain with the
root. No physical UART or DMA device is assigned to the inmate.

## Source and validation scope

The configurations preserve the resource layout used by the SMRS dual-OS
bring-up in November 2026. Build these C sources with **this** Jailhouse tree;
do not copy previously generated `.cell` files into another build.

The XZB100 layout originated from Jailhouse commit `6d21af02` plus the local
Linux compatibility/firmware-entry and AArch32 capability fixes. The root IRQ
list here removes a duplicate description of INTIDs 896–927: the last block
starts at 928, and the complete root set remains exactly INTIDs 32–991.

The XZA100 source layout was exercised with Phytium fork commit
`64bc5bf34651a0afc984aabbcc0ca8b7e3f88794`, under `src/jailhouse`. That fork and
this repository both label their formats revision 14, but their system and PCI
structures are **not binary compatible**. This port uses this repository's
ARM64 architecture field and explicit PSCI flag; it does not import the vendor's
unused multiple-ECAM/GICR extensions. The new XZA100 build has offline resource
checks, but still requires board regression testing with this hypervisor.
Historic vendor-fork success does not prove the new binary works on the board.

The guest DTS files contain no image-specific initrd addresses. The Linux
loader fills those from the actual image. Their interrupt maps select only
device 0/INTA and device 1/INTB, and their virtual-console property supports the
SMRS `hvc_jailhouse` driver. This console driver is an external Linux module,
not a physical UART emulation. Supply it in the inmate kernel/rootfs to use
`console=hvc0`. SSH credentials and service policy belong to that rootfs and
are not enabled by these device trees.

## Required software

Use the ARM64 kernel-compatibility changes accompanying these configurations:

- Linux 5.15/6.6 mapping support, including exact RX/NX Linux-side firmware
  entry mappings bound to the firmware built with the module;
- the AArch32-at-EL1 capability check before accessing `FPEXC32_EL2`, required
  for the Orin Cortex-A78AE;
- the SGI pending/active delivery and pending-queue ordering fixes;
- the Linux loader changes that accept CPU-only loadable RAM without granting
  it `JAILHOUSE_MEM_DMA`, and account for the kernel runtime footprint and
  expanded initramfs capacity.

The loader changes are maintained separately from board configuration. Do not
work around a loader failure by adding DMA permission to guest RAM. Use a
matched firmware/module/cell/tool set; regenerate the firmware entry layout
when the firmware changes.

The tested kernel families are L4T 5.15.148 on XZB100 and the board-patched
openEuler 6.6 kernel on XZA100. Both use 4 KiB pages, a non-VHE root execution
context and disabled KVM ownership of EL2. Enable the configuration and symbol
lookup requirements documented by the kernel-compatibility changes. The SMRS
repository retains the complete kernel/rootfs builders, resource collectors,
NFS state and application deployment logic under `platform/xzb100`,
`platform/xza100` and `platform/heterogeneous`.

## Resource contract

All ranges below are physical and use inclusive start/exclusive end semantics.
The exact CPU topology, RAM holes and interrupt availability must be audited
again after changing firmware, board SKU, memory size or kernel device tree.

| Resource | XZB100 | XZA100 |
|---|---|---|
| Hypervisor (16 MiB) | `0xc0000000–0xc1000000` | `0xb0000000–0xb1000000` |
| Shared reservation (16 MiB) | `0xc1000000–0xc2000000` | `0xb1000000–0xb2000000` |
| Inmate RAM (512 MiB) | `0xc2000000–0xe2000000` | `0xb2000000–0xd2000000` |
| CPU7 MPIDR affinity | `0x10300` | `0x301` |
| GIC distributor | `0x0f400000` | `0x29a00000` |
| Root GIC redistributor base | `0x0f440000` | `0x29b00000` |
| CPU7 redistributor frame | `0x0f520000` | `0x29be0000` |
| Virtual PCI ECAM / BAR aperture | `0x0f800000 / 0x0f900000` | `0x34000000 / 0x34100000` |
| Root endpoint INTIDs | 590, 591 | 105, 106 |
| Inmate endpoint INTIDs | 588, 589 | 101, 102 |

The first 64 KiB of inmate physical RAM is aliased at guest address zero for
the loader. The rest is identity mapped. The communication page is separate
at guest address `0x80000000`. GIC/ECAM/BAR windows are trapped rather than
included in direct memory mappings. All enabled and disabled root DT nodes,
PCI parent windows and current IRQ owners must be checked for collisions.

The first endpoint is protocol-undefined ivshmem with three peer slots:
root ID0, unused ID1 and inmate ID2. Its state table is read-only, common R/W
area is writable by both cells, and each cell may write only its own output
slot. The second endpoint uses VETH with root ID0 and inmate ID1. Empty VETH
R/W region 6 is intentional and must not shift later region indices.
Both endpoints use INTx, not MSI. The root initially owns the full implemented
SPI set and gives the inmate its two endpoint IRQs during cell creation.

Root RAM mappings retain load access to the future inmate region, which
Jailhouse removes from the root during assignment. Root peripheral mappings
are broad, and no IOMMU unit is configured. CPU partitioning and the absence of
guest DMA do not establish protection from a faulty root-owned DMA master,
shared SoC failure, shared power or shared memory hardware failure.

## Root Linux boot prerequisites

The boot DT must reserve all three hypervisor/shared/inmate ranges above as
`no-map` before Linux allocates them. Preserve the board's actual memory
layout and firmware reservations. In particular the XZB100 root RAM array
reflects measured high-memory carve-outs; it is not a generic 64 GiB map.
Root DT generators and current-boot memory/IRQ checks live in SMRS. Do not
pre-create `/pci@0` in the boot DT: the Jailhouse driver installs the root's
virtual PCI node after enable.

XZB100 bring-up used `kvm-arm.mode=nvhe cpuidle.off=1 arm64.nopauth`, with
`efi=noruntime,debug initcall_blacklist=optee_driver_init` and a root DT that
keeps OP-TEE from binding. Those restrictions avoid previously observed
idle/firmware interactions; this configuration does not add Tegra SiP/OP-TEE
forwarding or SMMU ownership support.

XZA100 bring-up used `pci=nomsi kvm-arm.mode=nvhe arm64.nopauth`. Keep the
board's real console/root filesystem arguments. Before enable, prove root
storage/network operation with legacy interrupts and verify no hardware MSI
users remain. The tested U-Boot loads the Image at `0x90200000` and its root DT
at `0xa0000000`; loading the DT at `0x93000000` overlaps that Image's runtime
footprint. Root firmware may rewrite memory and CPU nodes, so inspect the
resulting live DT and memblock reservations, not just the disk DTB.

In both cases keep CPUs 0–7 online before enable; do not substitute an offline
power-mode CPU for CPU7. The DTS affinity and physical redistributor frame must
agree with the current topology. Guest boot arguments preserve the tested
pointer-authentication and GIC LPI restrictions. The host driver creates the
virtual PCI bridge; no physical devices should be added to these inmate DTs.

## Offline validation

The normal `configs` build discovers all four C files and both DTS files.
For a kernel-independent check from the repository root:

```sh
CROSS_COMPILE=aarch64-linux-gnu- python3 tests/test_xz100_configs.py
```

This requires GCC/binutils for AArch64, `dtc`, `fdtget` and Python 3. It builds
in a temporary directory, parses this repository's configuration ABI, runs
`jailhouse-config-check`, and checks CPU ownership, RAM overlap, trapped
apertures, write permissions, IRQ sets, PCI peer IDs and DTS agreement. It
needs neither hardware access nor ignored SMRS build/evidence directories.

After moving to a new common Jailhouse build, repeat board checks in order:
root boot/resources, root-only enable/disable, CPU7 transfer/return, guest
Linux boot, both ivshmem endpoints/IRQ delivery, large-packet networking and
management access. Only then restore NFS-backed state and SMRS nodes. Offline
checks do not exercise CPU hotplug, firmware calls, DMA or fault recovery.
